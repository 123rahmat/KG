# KG vNext — Coding and Scholarly Research System Blueprint

**Design status:** build target, not a completed implementation (2026-10-10).
**Fundamental decision:** ONE shared KG runtime with TWO independent domain-control engines. See SHARED_KG_DOMAIN_CONTROLLERS.md.

## 1. Two first-class project chat workspaces

**Coding** shows repository, revision, files, scoped diffs, terminal/tests with real execution receipts, approvals, and delivered changes.
**Research** shows question, inspected source library, claims/citations, methods and datasets, calculations, tables/figures, manuscript structure and exports.

Use the same responsive chat infrastructure, authorization, execution machinery, model gateway, storage, budget and identity management. Separate agentic decisions, project-scoped context and workflows; do not duplicate whole systems. Code can inspect technical papers; Research can execute authorized mathematical/statistical code without changing controller identity.

For ordinary narrow tasks use a direct cheap response *in the relevant domain*. Do not force every request into planning, brainstorming or a permanent specialist team.

## 2. The adaptive execution loop

1. Observe the requested deliverable, authorized controller/project, current revision, relevant history and explicit constraints.
2. Understand whether this is a direct answer, implementation, exploration, proof, quantitative experiment, manuscript draft, editing, or critique. Clarify only genuinely missing material information.
3. Brainstorm alternatives *only when helpful*. Plan a dependency graph only when work is substantial, uncertain or explicitly requested.
4. Minimize context: reuse authorized unchanged repository indexes or inspected source excerpts. Search or retrieve only for important evidence gaps.
5. Choose the least expensive sufficient authorized model, tools and optional specialists. Recruit only roles with demonstrated independent information value and budget headroom.
6. Perform concrete work with scoped inputs: file mutations against pinned revisions, actual tests/runner receipts, inspected sources, reproducible analyses, saved figures and manuscript artifacts.
7. Verify acceptance with real evidence and domain-specific checks. Agents/models can critique but cannot declare their own unverified success.
8. On failure, diagnose from errors, invalidate dependent results and repair under finite budgets. On success, stop and deliver what was genuinely completed, including known limitations.
9. Reuse feedback only through governed project/controller-scoped learning, without expanding tool permissions.

**Important:** recommendations generated by control-workflow-policy.js are advisory. The existing shared RunStore is the ONLY persisted task and completion authority.

## 3. CodingControlEngine

The small path is direct technical explanation or one bounded change followed by relevant recorded checks. The large path is scoped architecture and dependency analysis, incremental implementation, selective unit/integration/build/security tests, diff review, bounded repair, and reproducible delivery.

Optional specialties: architect, implementer, debugger, testing, security, performance, UI/accessibility. Parallelize only independent analyses or writers with nonoverlapping paths at the same immutable base revision. Serialize dependency mutations, ambiguous paths, integrations and changed shared state.

Never say tests passed without an authenticated execution receipt. Report **Not run** if a required runner/tool is unavailable. Require explicit authorization for deployment and destructive/external changes.

**Acceptance:** requested functionality satisfied, correct revision, explicit change scope, actual relevant test/build results, reviewed differences, disclosed failures and authorized side effects.

## 4. ResearchControlEngine: all substantive paper/thesis components

**Question/protocol:** precise objectives, hypotheses, theory, discipline, inclusion/exclusion, method and success criteria.

**Literature and evidence:** deduplicate papers, prefer primary sources, DOI/version/provenance, inspect appropriate source passages, preserve source records independent of bounded model context. Every material claim maps to inspected evidence and counterevidence. Report unsupported claims, disagreement, publication bias and uncertainty. Never invent DOIs or quotations.

**Qualitative methods:** interviews, sampling, codebooks, thematic analysis, reflexivity, ethics and triangulation. Do not fabricate interview participants or quotes.

**Quantitative methods and mathematical work:** assumptions, variables/units, missing data, statistical models, effect sizes, confidence/uncertainty intervals, mathematical derivations, valid roots/domain restrictions, numerical cross-checks, reproducible environments/seeds and signed computational receipts.

**Figures/tables:** plot real approved data with reproducible transformations, truthful scales/axes/units, captions, uncertainty, accessibility and links to data/source versions. Generated conceptual images must be labeled illustrations, never observations.

**Manuscripts:** title, abstract, keywords, background/introduction, literature/theoretical framework, research questions, methods, analysis/results, discussion, limitations, conclusions, references and appendices, adjusted by discipline, journal and user request. Preserve traceable figures, tables, equations and citation keys through revisions.

**Review/delivery:** methodological critique, reference and claim checks, writing/editing, venue style, complete requested sections, versioned DOCX/PDF exports and rendered-output inspection.

Optional roles: scholar/librarian, methods expert, statistician, qualitative and mathematical analyst, figure specialist, academic editor, critical reviewer. They must not duplicate retrieval or fabricate findings.

**Acceptance:** relevant sections complete, evidence sufficient and traceable, methods/results reproducible when required, citations/figures valid, unresolved limitations visible and requested exports verifiable. If checks cannot be completed, deliver a clearly qualified draft.

## 5. Multi-reasoning, cost and quality

**Simple:** one efficient primary-model pass, no extra agents or mandatory plan.
**Moderate:** structured reasoning, just-in-time tools and targeted verification.
**Complex/uncertain/high-risk:** independent specialist perspectives only when there are meaningful open unknowns, conflicts, code/test failures or complex architecture decisions.
**Recovery:** stop repeated low-value speculation, use actual failure evidence, escalate reasoning only when warranted.

Set per-request budget and optional-agent ceilings; never spend a concurrency ceiling as a target. Initial tuning may allow up to four independent controller work lanes when proven safe, but measure actual value. Preserve a shared user/provider budget. Cache only by authorized controller, project, source/revision, policy and context. Stop at evidence-satisfied acceptance or hard limits, without suppressing mandatory verification to save optional reviewer tokens.

Measure accepted-task quality, cost per accepted output, token consumption, p50/p95 latency, missing/unsupported claims, genuine test pass rate, source continuity, recovery success and fairness of Coding/Research capacity. Use recorded benchmarks, not invented improvement figures.

## 6. True isolation over one system

Every project-bound request, run, task, agent invocation, memory record, source, artifact, cache item, lease and worker message must be checked against server-verified principal, tenant workspace, project, owning controller, run and input revision. UI-selected surfaces never grant authority. Use logical queue partitions and fair shared-worker reservations; do not duplicate the task lifecycle, provider connection, tool registry, database or billing service.

Cross-controller project transfer requires explicit authorized versioned read-only/copy handoff; incidental cross-domain methods remain inside the original controller. Switching chat tabs cannot retarget work, share credentials or merge private context.

## 7. Required regression matrix

Coding: direct explanation, tiny repair, full API build, repo revision mismatch, overlapping parallel writes, changed dependency, failed tests and bounded recovery, nonexistent runner.
Research: inspected paper summary, humanities/qualitative thesis, large manuscript, systematic literature review, statistical root exclusions, charts/units/provenance, conflicting sources, fake DOI detection, more than 40 sources with old citations still linked.
Security: malicious project label, off-topic/mixed request, cross-user/project/controller read, consent/policy revocation, late result after cancellation, prompt injection inside paper/code, provider exhaustion, replayed action.
UX: accessible mobile and desktop project chats with active controller, recorded progress, approvals, evidence, output artifacts and truthful cost/verification suggestions.
Operations: migration idempotency, isolated PostgreSQL/RLS fixtures, encrypted storage, queue fairness, worker recovery, audit, live model/tool and sandbox smoke checks.

## 8. Non-destructive implementation order

1. Finish domain understanding and control policy; prove tests.
2. Enforce domain admission and immutable controller/project identity in shared server routes, tasks, tools and database/RLS.
3. Implement fair logical controller queues and crash-safe agent invocation/handoffs using existing RunStore and workers.
4. Complete two dedicated chat/project views and genuine end-to-end Coding and Research vertical slices.
5. Add durable unbounded scholarly ledger, exact math/statistics, figures and full manuscript export/inspection.
6. Migrate old active callers; preserve historical data and existing migrations; retire unrelated active product paths.
7. Run full functional/security/quality/cost/UI/live integration suites and prepare rollback.

**Release rule:** keep the draft PR unmerged until complete integration evidence. Foundation code and advisory chat summaries are NOT proof the full two-controller product is ready.
